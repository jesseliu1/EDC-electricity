# ASNS 宿主层连线设置与多通道绑定重构建议

## 1. 这次纠偏后的核心结论

当前宿主原型里把三件事混在了一页里：

1. 系统级连接
2. 系统级通道资源管理
3. `EDC electricity` 这个具体应用的业务字段映射

第 3 件事不应该出现在宿主层。

正确层级应为：

```text
ASNS 宿主层
├── 连线设置
│   ├── 后台连接
│   ├── 通道同步
│   ├── 通道目录
│   └── 系统级标准化绑定
│
└── 应用商店
    └── 已安装应用
        └── EDC electricity
            ├── 打开应用
            └── 配置
                └── 应用级字段映射
```

一句话：

- 宿主层负责“把数据接进来、整理好、标准化”
- 应用层负责“把这些标准化后的数据用到自己的业务字段上”

---

## 2. 宿主层和应用层分别应该做什么

## 2.1 宿主层 `连线设置`

宿主层页面里应该只出现“系统级、应用无关”的内容：

- EDC 地址、账户、密码
- 测试连接
- 同步设备/通道
- 连接状态
- 最近同步时间
- 原始通道目录
- 通道筛选、搜索、分组、预览
- 原始通道到“系统标准点位”的绑定

不应该出现：

- 功率
- 电压
- 炉温
- 炉压
- 任何只属于 `EDC electricity` 的业务字段

这些字段属于应用层，不属于宿主层。

## 2.2 应用层 `EDC electricity -> 配置`

应用层页面里才应该出现业务字段映射：

- 功率
- 电压
- 炉温
- 炉压
- 后续切割、基线、偏差分析特有字段

应用层不是直接面对“原始通道”，而是优先面对宿主层已经整理过的“系统标准点位”。

这样以后如果应用商店里有第二个、第三个应用：

- 它们共享同一套宿主连接
- 复用同一份标准化数据目录
- 只维护各自应用自己的字段映射

---

## 3. 推荐的两级绑定模型

## 3.1 第一级：宿主层标准化绑定

目标：

把 EDC 返回的原始 `suid/cuid` 通道，整理成“系统标准点位”。

建议宿主层引入一个中性概念：

`标准点位 / Standard Signal`

它不是某个应用的字段，而是平台级数据资源。

每个标准点位建议至少包含：

- 标准名称
- 标准编码
- 测量类型
- 单位
- 作用对象
- 位置/产线/设备归属
- 来源通道（一个或多个）
- 最近值
- 数据状态
- 标签

示例：

| 标准点位 | 说明 | 备注 |
|------|------|------|
| `active_power` | 有功功率 | 平台级标准点位 |
| `line_voltage` | 线电压 | 平台级标准点位 |
| `furnace_temperature` | 炉温 | 平台级标准点位 |
| `furnace_pressure` | 炉压 | 平台级标准点位 |
| `humidity` | 湿度 | 平台级标准点位 |
| `digital_state` | 数字状态 | 平台级标准点位 |

关键点：

- 这里出现的是“平台级语义”
- 不是某个应用自己的字段合同

## 3.2 第二级：应用层业务字段映射

目标：

把平台级标准点位绑定到某个应用自己的业务字段。

例如 `EDC electricity`：

| 应用字段 | 来源 |
|------|------|
| 功率 | `active_power` |
| 电压 | `line_voltage` |
| 炉温 | `furnace_temperature` |
| 炉压 | `furnace_pressure` |

这样应用层就不直接面对 2000+ 原始通道，而是面对一层已经整理好的“标准点位目录”。

## 4. 大量通道绑定的最佳交互实践

## 4.1 不推荐：纯树状逐层点击

纯树状的问题：

- 扫描效率低
- 对比多个通道困难
- 很难做批量处理
- 搜索结果与层级结构容易割裂
- 通道一多时，操作成本迅速上升

树状结构可以保留，但不应该成为唯一主交互。

## 4.2 推荐：筛选栏 + 结果表 + 详情/动作面板

对于 2000+ 通道，最佳实践通常是三段式工作台：

### 左侧：筛选与导航

用于缩小范围，而不是承担全部操作：

- 设备树 / 区域树
- 设备类型
- 单位
- 在线状态
- 是否有最近值
- 是否已标准化
- 搜索框

### 中间：结果表

这是主工作区。

建议用表格或列表，而不是纯树：

推荐列：

- 设备
- 区域
- 通道名
- `suid`
- `cuid`
- 单位
- 最近值
- 状态
- 当前绑定状态

支持：

- 排序
- 搜索高亮
- 多选
- 批量操作
- 快速预览

### 右侧：详情 / 绑定动作

右侧显示当前选中通道或批量选中对象的详情：

- 原始通道信息
- 最近值预览
- 数据更新时间
- 当前标签
- 当前标准化状态
- 可绑定的标准点位

右侧应承担动作，而不是把整套目标字段全摆出来让人来回点。

## 5. 宿主层的推荐页面结构

我建议宿主层 `连线设置` 最终拆成 4 个页签或步骤：

## 5.1 连接

- URL
- 账户名
- 密码
- 测试连接
- 最近同步
- 节点状态

## 5.2 通道目录

- 原始设备/通道目录
- 搜索
- 筛选
- 通道预览

这是“看全量资源”的页面。

## 5.3 标准化绑定

把原始通道绑定成系统标准点位。

这里的目标不是应用字段，而是平台级标准点位。

推荐布局：

- 左：筛选
- 中：通道结果表
- 右：标准点位绑定面板

## 5.4 同步记录 / 异常

- 最近同步时间
- 失败原因
- 哪些设备未返回
- 哪些通道无数据

这个页面很重要，因为真实联调阶段问题会很多。

---

## 6. 平台级标准化绑定的最佳操作方式

如果后面标准点位变多，推荐这样操作：

## 6.1 先筛，再选，再绑

流程：

1. 通过筛选和搜索缩小范围
2. 在结果表选择一个或多个通道
3. 在右侧把它们绑定到某个标准点位

不要走“先打开树，再逐项点”的流程。

## 6.2 支持批量操作

大量通道绑定必须支持批量：

- 同设备批量标记
- 同名称规则批量标记
- 按单位批量筛选
- 按关键词批量推荐

例如：

- 搜索“电压”
- 筛选单位 `V`
- 多选后批量绑定到 `line_voltage` 相关标准点位候选

## 6.3 支持建议与冲突提示

推荐做法：

- 根据通道名关键字给出建议标准点位
- 根据单位不匹配给出警告
- 对一个通道被多个标准点位占用给出冲突提示
- 对一个必需标准点位还没有来源给出缺失提示

## 6.4 支持“未绑定 / 已绑定 / 有冲突”三种主视图

这比只给一棵大树有效得多。

建议提供三个快捷过滤视图：

- 未绑定
- 已绑定
- 有冲突 / 待确认

用户每天最关心的通常不是“所有通道”，而是“还有哪些没处理好”。

## 7. 推荐 MVP 版本怎么做

为了不把系统做得过重，MVP 可以先这样落：

## 7.1 宿主层 MVP

先做：

- 真实连接
- 通道同步
- 搜索和筛选
- 原始通道目录
- 单条通道详情
- 平台级标准点位绑定

先不做：

- 拖拽
- 复杂批量规则引擎
- 自动推断并一键全绑定

## 7.2 应用层 MVP

先做：

- `EDC electricity -> 配置`
- 选择平台级标准点位
- 映射到应用业务字段
- 保存与校验

这样两层职责最清晰，也最容易讨论和迭代。

---

## 8. 当前宿主原型应该怎么调整

当前宿主页里最需要改的不是视觉，而是层级语义。

建议调整为：

### 当前宿主页面保留

- API 连接区
- 通道目录区
- 选中通道详情区

### 当前宿主页面移除

- 右侧 `功率 / 电压 / 炉温 / 炉压` 业务字段槽位

### 当前宿主页面替换为

- 右侧 `标准点位绑定` 面板

该面板显示：

- 当前选中通道
- 可绑定的平台级标准点位
- 当前绑定状态
- 保存标准化结果

---

## 9. 这轮推荐结论

结论如下：

1. 宿主层不应该出现 `EDC electricity` 的业务字段
2. 宿主层应该做“原始通道 -> 平台级标准点位”的标准化绑定
3. `EDC electricity` 应用层再做“标准点位 -> 应用业务字段”的映射
4. 面对大量通道时，最佳实践不是纯树，而是：
   - 左侧筛选
   - 中间结果表
   - 右侧详情/绑定动作
5. 树结构可以保留，但应降级为导航或过滤方式，而不是主操作方式

---

## 10. 下一步建议

在真正动手改 UI 前，建议先确认两件事：

1. 宿主层要不要正式引入“标准点位 / Standard Signal”这个平台级概念
2. `EDC electricity` 第一版应用级字段合同是否仍固定为：
   - 功率
   - 电压
   - 炉温
   - 炉压

这两个问题一旦确认，后续页面结构就会稳定很多。
