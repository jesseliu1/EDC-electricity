# ASNS 宿主层接入与 EDC electricity 应用层映射方案

## 1. 背景

当前项目 `EDC electricity` 将不再作为独立系统直接承担全部连接职责，而是作为
`ASNS（AI Sensory Nervous System）` 应用商店中的一个业务应用被嵌入。

参考目录：
- `docs/Ref/asns（ai-sensory-nervous-system）ai感知神經系統`
- `docs/Ref/EDC AI通信基座API使用說明書.docx`

已确认事实：
- ASNS 参考目录是一套独立的 React + Vite 宿主系统原型，包含 `connect / store / devices / dash` 等系统级页面。
- EDC 网关接口并非 REST 资源风格，而是：
  - `POST /login` 获取全局 `token`
  - `POST /systemcfg` 通过 `request` 字段执行指令
  - `ws://{HOST_IP}:1127` 提供实时推送
- 设备定位采用双层 ID：
  - `suid`：设备/传感器 UID
  - `cuid`：通道 UID

## 2. 职责边界

### 2.1 ASNS 宿主层负责

- 后台系统连接
- EDC 登录鉴权与 token 生命周期管理
- 设备/通道发现
- 系统级连接状态展示
- 为已安装应用提供可选的数据源清单

### 2.2 EDC electricity 应用层负责

- 使用哪些通道来驱动本应用业务
- 将后台通道映射为本应用业务字段
- 基于映射后的数据进行基线、炉次、偏差、任务、报表等业务处理

### 2.3 明确不应由应用层承担

- 重复维护一套 EDC 登录逻辑
- 在每个应用里各自保存一份独立的系统连接配置
- 把“系统连接”和“业务字段映射”混成一个设置面板

## 3. 推荐信息架构

推荐采用以下页面层级：

```text
ASNS
└── 应用商店
    └── 已安装应用
        └── EDC electricity
            ├── 打开应用
            └── 配置
                ├── 数据源映射
                ├── 映射校验
                └── 应用级参数
```

## 4. 配置页推荐落点

结论：

**参数映射配置页应放在**
`应用商店 -> 已安装应用 -> EDC electricity -> 配置`

原因：

- 连接 EDC 是系统级能力，属于 ASNS 宿主层。
- 映射规则是“本应用如何理解这些通道”，属于应用级能力。
- 后续如果应用商店里还会有别的应用，不同应用对同一套设备数据的使用方式可能不同。
- 将映射配置挂在应用下，可以避免把系统连接页做成业务规则堆积区。

## 5. 推荐配置页结构

建议拆成 3 个区块。

### 5.1 区块 A：连接来源

只读展示，由 ASNS 宿主层提供：

- 当前连接的 EDC 主机
- 连接状态
- 最近同步时间
- 当前可用设备数 / 通道数

这个区块的目标是让用户知道“你现在映射的是哪一套后台数据”，但不在这里重新登录。

### 5.2 区块 B：业务字段映射

这是核心区块。建议一行一个业务字段：

| 业务字段 | 用途 | 映射对象 |
|------|------|------|
| 功率 | 实时曲线、基线对比、炉次切割 | `suid + cuid` |
| 电压 | 实时曲线、基线对比 | `suid + cuid` |
| 炉温 | 基线对比、异常分析 | `suid + cuid` |
| 炉压 | 高功率基线等扩展指标 | `suid + cuid` |

每条映射建议展示：

- 字段名称
- 来源设备名称
- 来源通道名称
- `suid`
- `cuid`
- `chnDim`
- 是否已映射
- 最近样本值

### 5.3 区块 C：映射校验

保存前执行校验：

- 是否所有必填字段都已映射
- 单位是否符合预期
- 最近 N 分钟是否能取到值
- 是否存在重复映射到同一通道

## 6. 为什么映射层必须存在

因为 EDC 返回的是设备/通道模型，不是业务语义模型。

EDC 只知道：
- 某台设备
- 某个通道
- 某个单位
- 某个时间序列

但本应用需要知道：
- 哪个通道是“功率”
- 哪个通道是“电压”
- 哪个通道是“炉温”
- 哪些字段参与炉次切割、基线建模、偏差分析

因此必须通过映射层把 `suid/cuid` 转成本应用内部的标准业务字段。

## 7. 推荐接入顺序

后端真实接入建议按下面顺序推进，而不是直接替换所有 mock。

### Step 1：EDC 连接闭环

- 登录获取 token
- 获取传感器 / 通道清单
- 测试连接成功 / 失败

目的：
- 先确认网关可达、认证可用、设备清单可读

### Step 2：映射配置闭环

- 从 ASNS 宿主层拿到可选设备 / 通道
- 在应用配置页保存业务字段映射
- 完成映射校验

目的：
- 先把“哪些数据可用”这件事定义清楚

### Step 3：单条历史查询闭环

- 针对某个已映射字段调用 `getLocalDatas`
- 验证时间范围、字符串解析、单位、空值处理

目的：
- 先打通最基本的历史数据读取

### Step 4：业务页面逐步替换

- Dashboard 实时曲线
- 炉次切割输入
- 炉次详情对比
- 基线向导候选曲线

目的：
- 避免一次性把所有页面同时切到真实数据，降低排错难度

## 8. 当前项目的建议结论

对 `EDC electricity` 当前仓库而言，下一阶段不是直接“全面接入后台”，而是：

1. 先在后端补 EDC client 能力
2. 明确宿主层连接和应用层映射的边界
3. 预留应用级映射模型
4. 先打通一个最小可验证链路：
   - 登录
   - 拉设备清单
   - 选择通道
   - 查一段历史数据

## 9. 待确认事项

后续进入真正实现前，还需要你确认这几件事：

- ASNS 宿主层最终是否负责统一保存 EDC 凭证
- 应用层映射配置最终保存在 ASNS 中，还是由本应用后端持久化
- 当前 MVP 的必填业务字段集合是否固定为：
  - 功率
  - 电压
  - 炉温
  - 炉压
- 后续炉次切割是否需要额外映射特殊信号，而不只是上述业务字段
