## 0. 本文档说明

### 0.1 UAT 定义

用户接受测试（UAT）验证系统在真实使用路径下是否满足商业交付标准。
UAT 不是后台接口自动化，而是从用户视角出发的完整操作路径验证。

### 0.2 后台测试 vs UAT 的区分

| 维度 | 后台测试 | 正式 UAT |
|------|----------|----------|
| 范围 | API / service / 单测 | 用户可见操作路径 |
| 证据要求 | 脚本断言 + 日志 | 截图序列 + 回看结论 |
| 截图 | 不强制 | 每个交互步骤必须截图 |
| 通过标准 | 断言通过即可 | 脚本通过 + 截图回看同时成立 |
| 落点 | CI / pytest / e2e spec | 本文档 + test-reports/ 目录 |

本文档仅覆盖 UAT 部分。后台测试（pytest / Playwright 自动化）另见 `docs/testing.md`。

### 0.3 截图与回看强制要求（摘自项目规范）

1. UAT 中每一次用户交互操作（点击、提交、切换、弹窗、跳转）都必须截图留存。
2. 截图完成后必须回看，回看是正式步骤，不是默认假设。
3. 回看必须记录：回看结论（通过/不通过/异常）+ 回看依据（图中看到了什么/没看到什么）。
4. PASS 判定必须同时满足：脚本/操作符合预期 + 截图回看通过。
5. 发现 bug → 录入 `docs/ui_issues.md` → 修复 → 回归验证。

### 0.4 截图目录约定

```
docs/test-reports/assets/UAT-EDC-ASNS-<YYYY-MM-DD>/<suite-id>/
  NN-<动作描述>.png
  screenshot-review.json
  evidence.json
```

截图文件名必须包含步骤序号和动作含义，例如：`01-asns-settings-page.png`。

### 0.5 Bug 流程

```
发现 bug
  → 录入 docs/ui_issues.md（含截图路径、复现步骤、预期 vs 实际）
  → dev 修复
  → QA 回归（重跑对应用例，补截图，更新回看结论）
  → 回归通过后标记 RESOLVED
```

### 0.6 通过标准总则

- 所有 P0 用例必须 PASS，不允许 FAIL 或 BLOCKED。
- P1 用例允许 1 个 BLOCKED（需记录原因），不允许 FAIL。
- 任何用例有未关闭 FAIL，不得放行商业交付。

### 0.7 换源确认专项口径

切换 EDC 源不再被视为普通保存动作，而是破坏性重建来源上下文。

只要满足以下条件：

- 当前操作会改变 `source identity`（`base_url + username`）
- 且当前系统仍存在来源相关状态（如已同步通道、已添加通道、活动基线、基线通道绑定、宿主连接摘要）

则正式 UAT 必须额外验证以下几点：

1. 在宿主点击 `测试连接`、`同步通道` 或 `保存设置` 前，必须先出现换源确认弹窗。
2. 弹窗文案必须明确说明“将清除旧来源相关配置”，不能只是泛化的“是否继续”。
3. 必须截图留存弹窗本身，确认图中能看到：
   - 当前是切换到新源
   - 旧来源相关配置会被清除
4. 用户点击 `取消` 时，本次动作不得继续执行，原运行态必须保持不变。
5. 用户点击 `确认` 后，才允许继续进入 `测试连接 / 同步通道 / 保存设置` 的原动作。

正式总账口径：

- `S04-TC02` 的 PASS 不再只看“新源连接成功且保存成功”。
- 如果切源前存在旧来源状态，但本次未出现换源确认弹窗，则本条必须判 `FAIL`。
- `S05` 的 PASS 也默认建立在 `S04-TC02` 已按上述确认口径通过的前提上。

### 10.4 uat-summary.md 格式

每次 UAT 执行完成后，在 Suite 目录平级创建 `uat-summary.md`：

```markdown

**执行日期**：<YYYY-MM-DD>
**执行人**：<姓名>
**环境**：prod / test
**总体结论**：PASS / FAIL / BLOCKED

## Suite 结论

| Suite | 结论 | 备注 |
|-------|------|------|
| S01 | PASS | |
| S02 | PASS | |
| S03 | PASS | |
| S04 | PASS | |
| S05 | PASS | |
| S06 | PASS | |
| S07 | PASS | |

## Open Bugs

无 / 见 docs/ui_issues.md

## 回看结论

所有截图已回看，回看结论见各 Suite 的 screenshot-review.json。

## 总账备注

- 涉及 `S04 / S05` 的总账备注必须单独写明：
  - 是否出现换源确认弹窗
  - 用户是点击 `确认` 还是 `取消`
  - 确认后继续的是 `测试连接` / `同步通道` / `保存设置` 哪条路径
- 不允许把“切源成功”简化成一句泛化结论，而不说明确认弹窗证据是否成立
```

### 10.5 留存要求

## 11. Bug 录入与回归规范

### 11.1 Bug 录入到 docs/ui_issues.md

发现 bug 时，立即在 `docs/ui_issues.md` 新增条目：

```markdown
## ISSUE-XXX: <简短描述>

- **发现日期**：<YYYY-MM-DD>
- **发现场景**：<UAT Suite ID / TC ID>
- **严重等级**：P0 / P1 / P2
- **复现步骤**：
  1. ...
  2. ...
- **预期结果**：...
- **实际结果**：...
- **截图**：`docs/test-reports/assets/<目录>/<文件>.png`
- **状态**：OPEN / IN_FIX / RESOLVED
- **修复 PR**：（修复后填写）
- **回归结论**：（回归后填写）
```

### 11.2 回归流程

```
bug OPEN
  → dev 确认并修复
  → 更新 ui_issues.md 状态为 IN_FIX
  → QA 重跑对应 TC
  → 补截图，更新 screenshot-review.json
  → 回归通过 → 状态更新为 RESOLVED
  → 回归失败 → 重新 OPEN，通知 dev
```

### 11.3 回归不通过不得关闭 issue

- RESOLVED 状态必须有回归截图证据支撑。
- 不允许仅凭 dev 口头确认关闭。

## 14. Codex Review 注意事项

以下几点请 Codex 在 review 时重点关注：

1. **用例覆盖完整性**：是否所有 7 个必覆盖场景都有对应 TC，无遗漏。
2. **前置条件依赖链**：TC 之间的 `前置` 依赖是否合理，有无循环依赖。
3. **截图步骤粒度**：每个 TC 的截图步骤是否足够细，能还原完整操作路径。
4. **回看要点**：每个 TC 的「回看要点」是否具体（有明确的「可见 X / 不可见 Y」），无模糊描述。
5. **Bug 流程闭环**：`docs/ui_issues.md` 是否有对应的已知 bug 条目需要补充。
6. **S04/S05 切源场景**：是否需要补充「切源中途网络中断」等边界用例。
7. **优先级分配**：P0/P1 分配是否与商业交付风险匹配。
8. **与现有 E2E spec 的重叠**：`apps/web/e2e/asns-edc-source-switch-reset-uat.spec.ts` 已覆盖部分切源场景，建议 Codex 确认 UAT 手工用例与自动化 spec 的分工边界，避免重复执行。
