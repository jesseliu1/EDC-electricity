## 现场验证结果

### 1. `3001/8001` 仍是当前最干净的正式链路

- `GET http://127.0.0.1:3001/` → `200`
- `GET http://127.0.0.1:3001/edc/` → `200`
- `GET http://127.0.0.1:8001/api/settings/runtime-status` → `overall_code=ready`

这说明若继续正式跑 `S05`，优先应走 `3001 -> 8001`，不要再沿用 `8000` 的历史脏状态。

### 2. `8000` 重启后暴露出持久化旧状态

重启 `8000` 后，读取到的持久化状态为：

- `edc_base_url=http://61.216.55.133`
- `active_baseline_id=baseline-001`
- `host_channels.total=8`
- `host_connectivity_status.is_connected=false`

这说明 `8000` 当前不是一套“刚完成 S04 切源”的干净状态，而是历史持久化状态回灌后的混合态，不宜直接拿来作为正式 UAT 依据。

### 3. source B 的真实设备 ID 与旧绑定不一致

直接查询 `http://61.216.55.133 / admin / admin` 后确认：

- source B 只有 `3` 台设备
- 典型 `suid` 为：
  - `2752`（表后电力）
  - `2755`（表前电力）
  - `300000000000000000001`（储能柜）

其中电压通道示例：

- `2752-128` → `A相電壓 (或VAB)`
- `2755-128` → `A相電壓 (或VAB)`

而当前 `8000` 持久化回来的宿主/基线绑定仍是旧源风格：

- `2349-199`
- `2349-128`
- `2054-128`
- `769-128`

这批 `suid/cuid` 不属于 source B 的真实目录。

### 4. 直接拉 source B 上的旧绑定通道，24h 内仍为 0 点

使用 `EDCClient` 直接查询：

- 通道：`2349-199`（功率）
- 通道：`2349-128`（电压）
- 时间窗：`5m / 1h / 24h`

结果：

- 登录成功
- 两条通道在三个时间窗内均返回 `0` points

这进一步说明，当前现场更像是“绑定仍是旧源通道 ID”，而不是简单的“新源本身没有数据”。

## 当前结论

- `S05` 当前不应再按 `8080` 阻塞描述
- 当前更真实的阻塞是：
  - 旧源 `suid/cuid` 绑定仍残留在某些运行态里
  - 若以这些旧绑定去读 source B，自然拿不到实时点
- 继续推进 `S05` 时，应优先在 `3001 -> 8001` 这条干净链路上重新执行：
  - `S05-TC01` 同步 source B 通道目录
  - `S05-TC02` 重新绑定 source B 的功率/电压/温度通道
  - `S05-TC03` 再验证 Dashboard 数据出现
