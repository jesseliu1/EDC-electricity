# 宿主与后端运行时收口方案

> 目标：结束“ASNS 宿主直接跑主仓、EDC 后端跑 runtime 副本”的混合部署模型，把代码真源、发布运行时、持久化数据三层边界立住。

---

## 1. 问题定义

当前线上存在一条危险混搭链路：

- `ASNS` 宿主 service 直接指向主仓目录
- `EDC` 后端 service 指向独立 runtime 副本

结果是：

1. 同一次“部署”实际上没有一个统一的发布对象
2. 只要有人只跑了前端 / 宿主发布脚本，没有同步后端 runtime
3. 线上就可能出现“宿主是新代码，8001 后端还是旧代码”的分叉状态

这不是缓存问题，也不是偶发漏操作，而是部署模型本身不一致。

---

## 2. 根因

当前模型把三种东西混在一起了：

### 2.1 代码真源

- GitHub
- 主仓：`/home/openclaw/projects/EDC-electricity`

### 2.2 运行时

- 后端：`/home/openclaw/edc-electricity-server`
- 宿主：直接跑主仓 `docs/Ref/asns（ai-sensory-nervous-system）ai感知神經系統`

### 2.3 数据与配置

- 后端 SQLite：`/home/openclaw/edc-electricity-server/data/asns.db`
- systemd user service
- nginx / webroot 发布面

问题在于：

- 后端已经有独立 runtime 边界
- 宿主却还在直接消费主仓工作目录
- 两边没有共同的“发布产物”概念

---

## 3. 正确模型

以后统一按三层处理：

### A. 代码真源层

- 只认 GitHub 和主仓
- 所有代码修改先进入主仓

### B. 发布运行时层

- `EDC` 后端运行时目录
- `ASNS` 宿主运行时目录
- systemd service 只能指向运行时目录，不再直接指向主仓

### C. 数据与环境层

- SQLite 数据库
- `.logs/`
- `backups/`
- systemd 环境变量
- webroot 静态发布目录

这三层必须分开：

- 改代码，只改主仓
- 部署时，从主仓生成运行时
- 运行时只负责执行，不再充当开发目录
- 数据目录独立保留，不被代码覆盖

---

## 4. 本轮决策

本轮不把生产直接改成“从主仓运行”。

本轮固定采用：

- 后端继续运行在独立 runtime 副本
- 宿主也切到独立 runtime 副本
- 两个动态 service 统一由部署脚本从主仓发布到 runtime

这样做的原因：

1. 能避免主仓未提交改动被线上直接读取
2. 能让宿主和后端拥有一致的发布语义
3. 能把“代码更新”和“数据保留”清晰拆开
4. 能为后续单入口部署脚本打基础

---

## 5. 本轮落地原则

### 5.1 service 指向统一

- `edc-backend.service` 指向后端 runtime
- `asns-host.service` 指向宿主 runtime

### 5.2 部署入口统一

部署脚本必须负责：

1. 从主仓构建
2. 清理旧运行库
3. 重建运行依赖
4. 复制最小运行文件
5. 重启 service
6. 做最小健康检查

### 5.3 数据目录独立

后端：

- 保留 `data/`
- 保留 `.logs/`
- 保留 `backups/`
- 不保留旧 `venv/`

宿主：

- 保留 `.logs/`
- 保留 `backups/`
- 不保留旧 `node_modules/`
- 每次重新安装生产依赖

### 5.4 不再允许混合发布

以后不再接受以下状态：

- 宿主直接跑主仓
- 后端跑 runtime 副本
- 只更新其中一边却称为“整站已部署”

---

## 6. 对外操作口径

以后默认只认这条链路：

`GitHub -> 主仓 -> 运行时副本 / webroot -> systemd service`

不是：

`GitHub -> 主仓直接运行`

也不是：

`主仓一部分直接运行 + 另一部分先复制再运行`

---

## 7. 完成标准

满足以下条件，才算本问题收口：

1. `asns-host.service` 不再直接指向主仓目录
2. `publish-edc-web-and-asns.sh` 会把宿主发布到 runtime 副本
3. 后端与宿主都遵守“运行库不保留，部署时重建”的规则
4. 文档中不再保留“ASNS 直接从主仓运行”的旧口径
5. 后续一轮完整部署后，不会再出现“宿主是新包、8001 还是旧后端”的结构性分叉

---

## 8. 一句话结论

问题不在于“后端为什么有副本”，而在于“宿主和后端没有采用同一种发布模型”。

正确做法不是取消 runtime，而是把宿主也收口到同一种 runtime 发布模型里。
